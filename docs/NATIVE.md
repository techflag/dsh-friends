## 完整真实链路：7 项通过

入口：`tests/desktop-network.mjs`。最终包在真实 WorkDSH Desktop 与独立官方 DSH Web 中验证，使用合成身份与真实第三方公共中继：

1. 两端运行同一包，Host 报告 `0.1.0-alpha.4`，Client 与 Host 版本一致。
2. 尚未建立联系人关系即可连接公共大厅。
3. 原生桌面实际发出公共事件，对端尚未创建发言身份时已收到，并在界面显示。
4. 首次回复创建身份后保留草稿和引用对象；双方不加好友也能公开讨论。
5. 重复提交同一操作只产生一个公共事件。
6. 大厅昵称 → 私聊申请 → 对方接受 → 加密文字实际到达另一端，联系人显示来自公开发言的昵称。
7. 核对两端身份不同，并保存原生界面截图及各节点状态。

本机候选节点：`wss://relay.damus.io`、`wss://relay.primal.net`、`wss://nos.lol`。发送记录中有实际 ACK；最低一个 ACK 才表示已发出。三节点在最终验证中均出现私聊就绪，但不代表每一条消息均被三节点接受。

详细的本机机器记录是 `.artifacts/desktop-network-verification.json`，包含检查结果与公开事件 ID，不包含私钥。初始两个已安装桌面的公共链路记录另存于 `.artifacts/older-desktops-public-proof.json`。

真实链路测试需明确授权；脚本有 `DSH_FRIENDS_ALLOW_PUBLIC_TEST=1` 开关，不进入默认 CI。可用 `DSH_FRIENDS_USE_WEB_GUEST=1`、`DSH_FRIENDS_DESKTOP_A_PORT=18822` 选择本轮隔离桌面与 Web 对端；Web 对端为已启动的 18808 测试实例，认证地址仅从本机日志读取，不输出 token。

## 本轮实际发现并修复

### 公共消息正常，私聊收不到

实际探测收到 Damus 的 `auth-required: requested filter requires authentication`。原实现把公共和私信过滤器放进同一个订阅，也没有 NIP-42，不能以“发送被接受”推断对方能读。

现实现分离大厅和私信订阅。已解锁且同意连接时，Host 仅针对已选中继的一次性挑战签署 NIP-42；验证后重新订阅私信。验证事件不广播，失败只影响私聊接收，不关闭公共大厅。以真实公网私聊收取及要求认证的回环中继双重验证。

### 更新后界面与 Host 不是同一版

旧底座中“立即启用”可能更新 Client，已经运行的同名 Host 实例仍被复用。现在快照报告实际后台版本，Client 检查并提示不一致。测试通过正常安装/组件启用和完整重启核对最终 Host 已更新，不用改官方代码或绕过安全存储保留明文密钥。

### 身份和收信配置

补齐 `inboxUrls` 的存储字段；解密历史使用经过 schema 处理的结果，兼容新增默认字段。公开发言后单独准备私信接收配置，不因此发布完整兴趣名片。联系人昵称从已验签公开发言保存，避免必须先加入发现才能识别私聊对象。

## 本地与原型检查

- `npm test`：9 组真实回环 WebSocket 测试。含 NIP-49 官方向量、损坏保护、交叉邀请、持久恢复、公共讨论、NIP-42 及公私订阅故障隔离。
- `npm run test:design`：13 项离线原型检查，CSP 禁止外部连接；只用于评审，不作为公网通过证据。
- 早期 `tests/native-ui.mjs` 对应 alpha.1 的名片优先界面，是历史验收脚本；当前公共大厅的真实入口以本页两个 desktop 脚本为准。

Host 仍使用官方 `storageDomain` 与 exact Fetch 路由 `/api/dsh-friends`，继承拥有者认证和来源检查。Client 通过官方 `sidebar.panellist` / `main` 插槽、Button 和 `--dsw-*` 主题变量接入。未增加独立账号后台，未改官方侧栏或 AI 对话。

独立 SDK Web 验收配置补齐了它自身的共享 peer 解析锚点，指向同一官方 SDK 的包；这是本机测试宿主配置，不是修改官方包的补丁，也不能替代正常 Desktop 安装验证。

## 尚未完成的发布门槛

不同物理设备/网络、Windows、macOS Intel、dataelement Desktop 实际操作、任意版本自动兼容、公共治理、完整历史归档/多设备同步未通过验收。最终包在官方旧版 Desktop 的私聊完整链路尚未重新自动跑完，不能拿 Web 结果替代该项。

因此只交付开发测试包，不创建正式 Release，也不承诺任意中继的长期可用性。公开名片实验 kind 30388 仍需后续类型冲突与节点策略检查；没有把 NIP-78 的拥有者私有数据当作公开目录。

## 最终恢复回归

公网和界面验收后，复查补齐后台维护对所有公共待发批次的恢复，及恢复后私信接收配置的准备。新增 3 条失败消息的重启回归：前两条在连接阶段发送，剩余一条由定时维护自动完成，无需反复点击。最终构建以 `runtimeRevision=lobby-recovery-1` 识别，避免同一开发版本内复用旧后台。消息列表对整个有界 ID 序列响应，覆盖同秒新增消息不改变末尾 ID 的情况。

最终构建另做了 6 项收尾核对（`.artifacts/final-build-verification.json`）：三个隔离桌面的实际修订与公钥、三个安装位置的 Host/Client 字节一致性、最终桌面构建与独立官方 Web 双向加密收信，以及模拟旧后台缺少新字段时明确提示重启且界面不崩溃。原有 a、b 口令保持不变；这里只解锁已知口令的合成验收身份。
